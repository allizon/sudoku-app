## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Let the player load a ◆PUZZLE by pasting its text onto the grid. In M0 this is parsing only: any text that parses is loaded as-is, with no validation and no solve (validation is M1, import §4). Builds on task-1, which provides the app, src/core/, and an empty grid on screen.

Spec: import.md §2 (paste on the grid) and §3 (formats, including parse errors). M0 rules, from docs/spec/milestones.md:
- Paste imports only onto an empty grid. Once a ◆PUZZLE is loaded, pasting is refused and the ◆PUZZLE is left exactly as it was. Reloading the page gives an empty grid again (nothing is saved in M0). Replacing a ◆PUZZLE is M1 (import §5).
- Parse errors, and the refusal above, appear as a toast in the top-right corner. This is interim; M1 may revisit.

Fixtures: this task also generates two fixture ◆PUZZLEs, for use in testing and in UI acceptance (the later tasks need a ◆PUZZLE to load, and Alix needs one to paste when reviewing). Keep them where tests and the UI checks can both reach them, and note their location in the handoff.

Not in this task: the I import field (M1), validation (M1), saving the ◆PUZZLE (M1). Use the terms in CONTEXT.md exactly.

- [x] #2 The parser removes all whitespace (spaces, tabs, line breaks) and commas, expects exactly 81 characters, and reads them left to right, top to bottom
- [x] #3 1–9 are read as ◆GIVENs; ., 0, and - are read as empty cells
- [x] #4 An 81-character string, nine lines of nine, and comma- or space-separated variants all load the same ◆PUZZLE

- [x] #7 Text with a character other than those above is rejected with a parse error naming the character and its position
- [x] #8 Text that leaves other than 81 cells is rejected with a parse error stating the count (e.g. "found 79 cells, expected 81")
- [x] #9 A rejected paste leaves the grid exactly as it was
- [x] #10 Pasting while a ◆PUZZLE is already loaded is refused and leaves the ◆PUZZLE exactly as it was
- [x] #11 Parse errors and the refusal appear as a toast in the top-right corner
- [x] #12 Parsing lives in src/core/ and is covered by unit tests; the paste handling and toast are covered by UI tests
- [x] #13 Two fixture ◆PUZZLEs are generated and available to both tests and UI acceptance checks, with their location noted in the handoff
- [x] #14 No focus ring or outline is drawn around the grid while it has focus, however focus arrived (page load, Tab, click)

- [x] #16 The flash color comes from a CSS token and does not obscure ◆GIVENs

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Decisions settled with Alix at the tests checkpoint (spec gaps for the handoff):
- Fixtures: fixtures/puzzles/puzzle-{1,2}.txt (nine lines of nine, '.' empty) with puzzle-N.solution.txt; generated by scripts/generate-puzzle.py from seeds 1 and 2. Each has exactly one solution.
- Parse error position: "unexpected 'x' at row R, column C", counted after whitespace and commas are removed; only the first bad character is named; a bad character counts as a cell.
- Count error: exactly "found N cells, expected 81".
- Both errors at once: two toasts, wrong count first.
- Refusal text: "A puzzle is already loaded — reload the page to start a new one." Unparseable text pasted onto a loaded puzzle shows only the refusal.
- Successful paste shows no toast. Toasts last 10 s or until clicked anywhere on them; they stack, each with its own timer.
- 81 empty cells do not count as a loaded puzzle.
- Whitespace means whatever JS \s matches (includes U+00A0, U+2003).
- Top-right placement is not checkable in jsdom; left to ux-reviewer.
